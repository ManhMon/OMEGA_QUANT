## 2. Fix 1: Reconcile Fallback Terminology and Metrics

### Issue

The original L2 report contained conflicting fallback metrics:
- Section 3 summary table: "Fallback Frequency: 0.0%" for both Clean and Clean+WG
- Section 7 text: "4 of 12 folds used fallback (folds 1, 2, 5, 7)"

Both validation reports also show "Fallback Candidate Frequency: 0/12 (0.0%)".

### Root Cause

Two distinct fallback concepts were conflated:
1. **Alpha Selection Fallback**: When the system cannot find any candidate alpha and uses a generic fallback. This is 0.0% because alphas were always selected.
2. **Winner Guard Fallback**: When the formulaic winner guard rejects all pre-guard candidates (due to negative validation IC) and falls back to the formulaic allowlist. This is 4/12 = 33.3% in folds 1, 2, 5, 7.

### Correction

**Alpha Selection Fallback** (reported in validation report Section 4):
- Clean: 0/12 (0.0%)
- Clean+WG: 0/12 (0.0%)

**Winner Guard Fallback** (Clean+WG only, from JSON `winner_guard_evidence.fallback_used`):
- Folds with fallback_used=true: 1, 2, 5, 7
- Rate: 4/12 (33.3%)
- Interpretation: In these 4 folds, all pre-guard candidates had negative validation IC, forcing the guard to use only formulaic allowlist members.

**Corrected L2 Report Section 3 Summary Table**:

| Metric | A: Full (prior) | B: Clean | C: Clean+WG |
|--------|-----------------|----------|-------------|
| Alpha Selection Fallback | N/A | 0.0% | 0.0% |
| Winner Guard Fallback | N/A | N/A (guard disabled) | 33.3% (4/12 folds) |

**Corrected L2 Report Section 7 Text**:

> **Winner guard fallback usage**: 4 of 12 folds used winner guard fallback (folds 1, 2, 5, 7). In these folds, all pre-guard candidates had negative validation IC, forcing the guard to select only from the formulaic allowlist (fml006, fml012, fml045, fml052, fml067). Alpha selection fallback was 0.0% in all variants.
