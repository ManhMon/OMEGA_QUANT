## 2. Findings

### Finding #1 (CRITICAL): TypeError in `_check_notional_limits` — dict-style access on itertuples

**Location**: `src/omega/quant/constraint_solver.py:148-153`

**Description**:
`itertuples(index=False)` returns namedtuples. Namedtuples support **attribute-style** access (`row.asset`) but NOT **dict-style** access (`row['asset']`). Line 148-151 uses `row['asset']` and `row['abs_notional']`, which will raise `TypeError: tuple indices must be integers or slices, not str` at runtime when a notional violation is detected.

**Evidence**:
```python
# Line 145-153 (current code - BROKEN)
violations = [
    ConstraintViolation(
        constraint_type="max_notional_per_asset",
        asset=row['asset'],              # <-- TypeError
        current_value=row['abs_notional'],  # <-- TypeError
        limit_value=self.config.max_notional_per_asset,
        excess=row['abs_notional'] - self.config.max_notional_per_asset,  # <-- TypeError
    )
    for row in violating.itertuples(index=False)
]
```

**Correct pattern** (as used in lines 199, 257, 282):
```python
asset=row.asset,
current_value=row.abs_notional,
excess=row.abs_notional - self.config.max_notional_per_asset,
```

**Impact**: Any portfolio with a position exceeding `max_notional_per_asset` will crash `validate_constraints()`, `adjust_trades()`, and `optimize_portfolio()`. This is a **production-blocking** bug.

**Root Cause**: Inconsistent migration — 3 of 4 itertuples call sites were correctly converted to attribute-style access, but `_check_notional_limits` was missed.
